1. **Deliver a complete Coach workflow.** A user can create a program manually or ask ChatGPT to produce the app's documented JSON, paste/import it, inspect every week, choose a start date, and follow it while recording actual results. Coach owns planning, daily check-ins, and progress; existing workout, run, and weight screens remain usable and share the same underlying records.

   The representative end-to-end case is a 26-week combined strength/running program, with several phases, reusable lifting workouts, changing run/walk intervals, equipment alternatives, nutrition targets, recovery check-ins, and body measurements. Support more than one session on a day. No exact personal weights, injury-clearance assumptions, or medical prescriptions should be hardcoded into the feature or test fixtures.

   | Required area | Deliverable | Completion evidence |
   | --- | --- | --- |
   | JSON plan import | Copy ChatGPT prompt, paste JSON, open plan file, strict validation, preview, draft, activation, export | A complete mixed program imports without retyping sessions; invalid or canceled imports create no plan |
   | Lifting | Prescribed sets/reps/ranges, actual load/reps, set completion, rest timer, effort, notes | Repeated Workout A sessions keep distinct actual results and completion |
   | Running | Structured warm-up, work/recovery repeats, cool-down; actual interval time/distance/pace; effort | Tracker executes the imported sequence, including pause and relaunch recovery |
   | Program | Completed, partial, skipped, moved, and pending sessions; phase/week progress | Home and Coach show the same dates and status, including two sessions in one day |
   | Progression | Previous comparable performance; explained suggestions; explicit accept/edit/dismiss | Suggestions affect selected future prescriptions, never past results |
   | Body | Existing weight history and trends, waist measurements, optional progress photos | Both Coach and Weight show the same weight record; photos survive relaunch and supported backup/restore |
   | Nutrition | Effective calorie/protein/carbohydrate/fat targets and manually entered daily totals | Partial entry stays partial; changing targets does not relabel past days |
   | Recovery | Sleep, soreness, energy, optional pain notes | Manual and available Health sleep sources are distinguishable and never added together |

3. **Organize Coach around Today, Program, and Progress.** Use a compact, accessible section picker within Coach. Daily entry forms open from Today and the relevant Progress page. Keep Ask Coach and AI history reachable through a labeled action, and keep all non-AI features available when the model is unavailable.

   | Surface | Contents and actions |
   | --- | --- |
   | Today | Active program and week; all today's sessions in order; Resume for an active session; compact nutrition and recovery cards; Log weight/waist shortcuts |
   | Program | Saved-plan library, Add Plan, active/draft/paused/finished/archived states; selected program overview; phase and week navigator; day/session editor |
   | Progress | Program adherence, lifting, running, body, nutrition, recovery detail pages with shared date-range selection |
   | Add Plan | Paste from ChatGPT, Import File, Build Manually, Create with AI when available |
   | Import Review | Summary, phases/weeks, exercise mappings, targets, issues, start-date preview, Save Draft, Start Plan |
   | Session Details | Prescription and last comparable results, equipment substitutions, start/resume, actual logging, finish/partial outcome |
   | Daily Check-in | Date, optional fields, saved source labels, and explicit save feedback; accessible independently of an active plan |

   Home consumes the same Today projection as Coach. It must not independently choose a different pending session or completion calculation. Today shows today's sessions first and a separate Overdue/Next area. An overdue session never blocks newer work. Empty state: Add Plan, Log a Workout, or Check In. Error and unavailable states retain manual entry. Do not place all seven full-size charts on the landing screen.

4. **Use the accompanying versioned JSON contract.** The normative schema and semantic rules are in [the JSON schema](../../WorkingOut/Resources/Coach/coach-plan-v1.schema.json) and [contract document](../../WorkingOut/Resources/Coach/coach-json-contract.md). [The example](../../WorkingOut/Resources/Coach/example-coach-plan.json) demonstrates format only; it is not a finalized training prescription.

   Implement the portable DTO with unconditional Foundation/Codable types, independent of FoundationModels. Manual authoring, JSON import, and optional AI generation produce the same DTO and use the same validator. Adapt the old WorkoutPlan type rather than breaking saved AI conversations. The schema file and Swift validation must agree; unknown fields, unsupported versions, invalid enum values, duplicate JSON keys, and unresolved references must not disappear through Codable's default behavior.

   Use reusable session templates, week patterns, explicit ordered weeks, stable phase/week/slot identifiers, and bounded interval repetition. Materialize stable local occurrence IDs once; never identify an occurrence solely by its day number or workout title. Persist the mapping from imported identities to local UUIDs. Units are explicit; represent unknown targets by omission, not invented zero values. Preserve source text when diagnosing a failed import.

   Copy ChatGPT Prompt includes the format/version, an example, the complete schema, and the user's manually chosen training requirements. Personal profile/history inclusion is opt-in with a readable preview. No automatic clipboard reads, uploads, ChatGPT login, or API connection are needed. Copy succeeds only when explicitly tapped. The parser may strip one enclosing JSON code fence, surrounding whitespace, and an initial UTF-8 BOM; it must not silently repair numbers, units, or malformed JSON with AI. The [in-app prompt builder](../../WorkingOut/Features/Coach/CoachPlanImportView.swift) generates the self-contained prompt from the same bundled schema and example, keeping the copied format consistent with import validation.

   Import stages are read bounded text, parse, validate, resolve exercises, expand a preview, and commit. Parsing/expansion happens away from the UI thread; model writes use an appropriate isolated context. Canceling before commit leaves no templates, exercise definitions, plan rows, events, or reminders. Save the plan, its revision, occurrence mapping, and owned prescriptions as one local unit of work. Report save failures and roll back this import without rolling back unrelated user edits.

   Exercise mapping uses a known library ID when available and exact normalized names otherwise. Ambiguous matches require selection. An unknown exercise may be created after review, with its display name and equipment retained. No fuzzy auto-substitution between different exercises. Repeated import of identical normalized content is a no-op/open-existing operation. A changed revision requires a diff; a matching program name or programId alone never authorizes overwrite. Draft replacement is allowed after review. For active plans, apply only explicitly selected unstarted future occurrences, retain prior revisions and past snapshots, or save as a new plan.

5. **Resolve personal-data storage before adding new records.** New Coach health/check-in records, progress photos, and personalized prescription/execution snapshots belong in a protected local store, configured without CloudKit and excluded from automatic cloud backup. This corrects the earlier broad suggestion that all new data could simply share the existing optional iCloud configuration. Apple's current review guideline 5.1.3(ii) prohibits storing personal health information in iCloud. [Apple review guidance](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)

   Use a Coach repository layer that can access local Coach records and existing activity repositories through IDs and value snapshots. Cross-store links must not be SwiftData object relationships. Reuse WeightEntry and the existing workout/run records as the historical identity source; do not create a second independent weight or activity history just for Coach.

   The current legacy schema already includes personal activity/weight records in an automatic-CloudKit configuration. The first implementation milestone must inventory those stores and establish a verified non-destructive transition before release. Recommended disposition: personal records become locally owned through shared repositories, preserving IDs, source links, and history in all tabs; retain any legacy cloud store for recovery until a separately reviewed migration retires it. Never silently disable existing synchronization, delete remote records, clear a store, or claim privacy compliance based only on the new store. Document the exact existing-sync impact for Joshua before that behavior change is implemented. This is a concrete storage/release decision, not permission to perform a remote migration in this planning task.

   Prototype migration against copies and disposable stores. Verify record counts, IDs, units, relationships, dates, execution state, old backup import, and rollback/relaunch recovery before switching the active repository. If the migration cannot preserve a historical field, surface it and retain the original record. Generic plan files and deliberate portable exports are distinct from automatically syncing personal tracking. Do not add a new backend.

7. **Define plan, session, and execution states precisely.** A program is draft, active, paused, finished, or archived. Keep one active combined program by default and many saved programs. Starting another names the current program and explains the resulting pause; do not discard it. Pausing a program does not erase an active workout. Archiving preserves actual history and check-ins.

   An occurrence is pending, in_progress, completed, partial, or skipped. Moved is schedule metadata, not a competing completion state. Past-due is derived from date; it is not automatic failure. Rest days have no workout execution and do not count as completed training. A phase that requires explicit readiness cannot advance simply because time passed or all days were skipped.

   A new execution begins only on Start, not when a program is imported or scheduled. Repeated Start resumes the same unfinished execution. Finishing with unfinished prescribed work offers Save Partial, Continue, or explicitly record completion with an explanation; no silent assumption that every prescribed set was performed. Manual Mark Complete without logs has provenance manual_attestation and no invented reps, weights, distance, or calories. Actual target attainment and user-recorded completion are separate concepts. Preserve terminal status when reconciliation reruns, including manually corrected and partial results.

   Migrate old workouts without an execution state as legacy_recorded. Preserve history and existing visibility; do not infer a completed percentage from default-false set checkboxes or reinterpret all old sessions as unfinished. New program progress includes only linked occurrences. Update streak/achievement/reporting readers so imported plans and newly prefilled, unperformed sessions cannot count as exercise. Define how legacy historical records retain prior behavior in tests.

8. **Implement lifting execution and rest timers.** The session opens with exercise order, technique notes, target rep ranges/time, optional load, effort guidance, rest, and comparable previous performance. Support warm-up versus working sets and explicit total/per-side counts; preserve current isolation semantics during migration. Support bodyweight/no-load movements without presenting unknown load as a real zero-pound performance. Per-set targets may differ.

   Use prefilled suggested input as a suggestion, not an actual result. Actual fields remain unrecorded until the user confirms or enters them. Log a set with explicit completion; correcting/unchecking it updates derived summaries. Record actual effort as labeled RPE or RIR, with one chosen scale rather than silently converting between them. Save exercise/session notes and substitutions. A substitution creates a snapshot of the performed exercise and retains the original prescription; it does not silently rewrite future days or mix unrelated performance histories.

   Rest timer supports start automatically after a completed working set when enabled, pause/resume, skip, and add/subtract time. Store a deadline or paused remaining duration and the set identity; the display refresh is not the source of elapsed time. Reopening after the deadline shows finished rather than restarting. Use normal notifications for background rest alerts if permission is granted; deny permission without breaking the timer. Do not promise precise background execution from a one-second SwiftUI timer. Limit observation updates to the active timer view. Close/dismiss means save and leave; Finish is a distinct action.

9. **Implement structured running on the existing tracker.** Expand warm-up, repeated work/recovery blocks, and cool-down to stable executable steps. A step has one prescribed termination target: elapsed active seconds or distance in an explicit unit, normalized to meters for tracking. Execution also supports deliberate manual completion, retaining the original target and recording that completion method. Pace and effort are optional guidance, not inferred injury clearance. Record actual step duration, distance, pace where measurable, user effort, and completed/partial/skipped state.

   Extend ScheduledRunTarget with a tagged plan reference that distinguishes a legacy RunningPlanSession from a canonical PlannedSession. Old recovery snapshots must still decode. Never reuse one UUID field with ambiguous model ownership. The existing plan-to-tracker flow remains the launch route; the generalized coordinator performs completion exactly once. Old source-plan wrappers become compatibility projections after migration, not another schedule authority. Disable legacy heuristic completion for canonically linked executions; imported Health runs may be proposed for association, but must not fabricate per-interval detail from an aggregate workout.

   Track step index, repetition, step baseline time/distance, pause intervals, completed step results, current partial result, and prescription revision in recoverable state. Pauses exclude paused time from step goals. A skipped interval stays skipped. Early finish creates a partial execution with preserved results. In-process background timing should derive from the active run's clock and samples; if relaunch cannot establish an accurate interval boundary, retain known data, restore paused, and label the gap. Do not manufacture completed intervals during an unknown interruption.

   Extend the existing recovery snapshot and use its established checkpoint/lifecycle strategy. Test live activity/locked-screen behavior independently on the device. On treadmills or absent location data, allow time/manual steps; distance/pace remains unavailable unless a real source or user input provides it. No fake GPS route or derived pace from missing distance. WorkoutKit/Watch-native scheduled workout delivery is not required for this Coach feature; reuse the current phone tracker and existing Health import.

10. **Make dates, edits, and program progression deterministic.** Anchor a program to a user-selected civil start date and timezone. Week patterns use day offsets from that anchor; label weekdays from the resulting dates. Store the intended civil date separately from execution timestamps. Travel does not silently move a Monday workout to Sunday or re-bucket past check-ins; detect timezone changes and offer a preview for future reminder/schedule behavior. Use calendar date arithmetic, not repeated 86,400-second additions across daylight-saving changes.

   Move edits only selected pending occurrences; maintain IDs and completion links. Multiple sessions on one date have explicit order. Swap, move-one, move-selected-future, repeat-week, and pause/resume show affected dates before applying. Repeating a week creates new occurrence identities; it does not erase an old week's results. Resume offers keep dates or shift remaining pending work by a shown offset. Started/terminal occurrences are excluded from bulk schedule changes. Changing the program start date after training began requires a future-only revision; actual timestamps stay fixed.

   Calendar and reminder services consume persisted occurrence dates and identities. Save locally first, then update projections. External errors leave a visible retryable state and do not report calendar success. Permission denial never blocks the in-app program. Export only user-selected events with neutral titles by default; do not insert health/pain notes into Calendar. Keep identifier mappings so repeated export updates the same app-created event. Update/cancel only mapped app events, never unrelated calendars. Resetting/reinstalling without mappings must not bulk-delete matching titles.

11. **Make progression explainable and reviewed.** Begin with deterministic rules and evidence from actual results. For a rep-range rule, require all prescribed working sets of a comparable exercise to meet the upper rep target, relevant effort criterion, and the configured number of successful sessions. Exclude warm-ups, skipped/partial/unlogged work, and substitutions unless equivalence was explicitly selected. Present the evidence and next load or rep target. Optional starting load means suggest establishing a baseline first.

   User sets the available load increment and confirms whether a dumbbell load is per hand. Apply only an explicitly approved change to selected future occurrences. Suggestion acceptance stores the decision and prescription revision; dismissal does not resurface the same unchanged suggestion. Editing source results invalidates pending suggestions. Avoid suggesting load increases when relevant soreness/pain feedback indicates the user wants to hold or reduce work; offer a review instead of diagnosis. Imported progression rules are named, supported rule types with bounded parameters, never executable formulas or code.

   Running progression follows imported phase/week targets and user-approved edits. Recovery/readiness gates stay explicit. No automatic pace recalculation, injury clearance, calorie reduction, or training-load increase based on the calendar, a single weigh-in, or a composite recovery score. Optional AI may explain or draft a suggestion, but acceptance and deterministic validation remain the same.

12. **Implement nutrition as daily totals with historical targets.** Store calories in kcal and macros in grams. Each field is optional: a blank protein entry is unknown, not zero. Support Save Draft for partial totals and Mark Day Finished when the user considers entry complete. Editing totals replaces the saved total for that date; it does not add the same number again. No meal database, barcode scanning, or automatic DFAC/MRE estimation is necessary for the approved manual-total workflow.

   Import program/phase nutrition targets and let users edit them with an effective date. Phase targets inherit only through documented whole-object replacement rules; do not guess missing values. Snapshot which targets applied to a logged day. Display target/actual/difference per known field; permit over-target values without shame language. Warn gently when supplied calories differ materially from 4P+4C+9F, but do not rewrite values or reject legitimate food-label differences. Never automatically eat back exercise calories or count active-energy expenditure as food intake.

   Only one selected program target applies to a day. Changing active plans does not overwrite previous targets or check-ins. Progress displays seven-day averages with the number of logged days and whether totals are partial; do not divide by seven while treating missing days as zero. Entry is available from Coach Today and Nutrition history even without an active program.

   Nutrition and recovery each have one daily record keyed by a Gregorian civil date, with timezone-at-entry retained as provenance rather than a second uniqueness key. Travel must not create two records for the same selected day. Editing a record's date into an occupied day requires a field-by-field merge preview; never silently add totals, replace notes, or discard either record. Keep measurement observations separate from this daily-record rule because multiple weight/waist samples on one date are valid.

13. **Implement body tracking without duplicate weight records.** Coach's weight chart and entry editor use the same repository as the Weight tab. Centralize existing weight import paths so source identity, sample corrections, deletions, and retries behave consistently. Preserve old entries with unknown provenance; do not guess which came from Health. New Health-derived records retain stable sample identity and source date. Deduplicate by source identity, not merely equal value or calendar day; several observations per day are valid. A chart may select a documented daily representative while retaining source samples.

   Waist entry records observation date, numeric value, cm/in unit, and optional notes; allow corrections and multiple measurements without implicitly overwriting another observation. Display unit conversion without repeated round-trip mutation of stored values. Weight trend uses a documented seven-day window over daily representative values, showing sample coverage; do not connect long gaps as measurements. Compare latest waist with a user-chosen baseline. No estimated body-fat diagnosis from weight, waist, or images.

   Photos are optional throughout. Use the system selected-item Photos picker, load only selected images, normalize orientation, resize for a documented maximum dimension, and remove location metadata from the app-owned copy. Initial resource defaults: select up to six images per import, reject source images above 25 MiB or 64 megapixels before full decoding, downsample the retained copy to a 2,048-pixel longest edge, and generate 512-pixel thumbnails. Process selected assets one at a time using bounded file-backed decoding; these limits can be adjusted after measured device validation. Store actual photo assets in a protected local directory and metadata separately; create thumbnails off the main thread and load comparison images on demand. A deleted Photos-library original does not delete the imported app copy, and deleting the app copy does not delete the library original. Communicate that distinction where the action occurs. Provide date/pose labels and side-by-side comparison without automated body analysis. [Apple selected-photo access](https://developer.apple.com/documentation/PhotoKit/selecting-photos-and-videos-in-ios)

   Photo import is a staged operation: validate and write temporary asset, commit metadata and finalized asset mapping, then report success. Cancellation or failed save cleans staged files. A later orphan cleanup must identify actual unreferenced staged assets and never sweep legitimate user photos. No photos in program JSON, prompts, notifications, public sharing, or analytics. Include deletion and user-selected backup/restore of app copies in the finished scope.

14. **Implement recovery with explicit sources and optional fields.** The check-in has sleep duration, soreness 0–10, energy 1–5, and optional pain location/score 0–10/notes. None is required to train or save another field. Keep zeros distinct from unknown values. These are self-reports; do not label them medical diagnoses or use them to claim an injury is healed.

   Default sleep display to the available selected Health source, with a manual entry option. Manual sleep overrides the displayed duration for that day but does not overwrite or add to underlying Health samples; retain provenance. Store total sleep duration, observation/end date, and sample coverage rather than a single score. Support shift workers: attach the main sleep episode to its wake date, allow the user to adjust the check-in day, and keep naps distinguishable. Reuse the existing interval-union/source-selection logic so overlapping device samples are not double-counted. Extend beyond the current latest-night method for date-specific history.

   When Health returns no readable data, display Not available and manual entry. Do not infer denied read permission, zero sleep, or no historical data from an empty result. Preserve manual entries when a Health query fails or changes later. Request only relevant types at the point of use, and do not write imported targets or self-reported pain into HealthKit. [Apple Health authorization behavior](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)

15. **Define progress calculations before building charts.** Program planned-session counts exclude rest entries, archived revisions, and duplicated import rows. Completed, partial, skipped, and pending counts remain separate. Required-session completion is completed required non-rest occurrences divided by scheduled required non-rest occurrences within the selected date range. Show optional completions separately; optional slots affect neither side of that fraction. An empty denominator displays No required sessions, not 0% or 100%. Label whole-program completion separately from adherence through today, so future sessions do not lower an adherence-to-date score. A week with all sessions skipped is resolved but not 100% completed. Phase readiness can remain awaiting review even when its calendar window ends.

   Lifting trends use actual completed sets with consistent exercise/equipment/unit/per-side interpretation. Missing loads do not imply a zero-load personal record. Running summaries compare actual distance/duration and interval outcomes against the original targets; compare pace only where distance and time support it. Nutrition and recovery charts show logged-day counts. Body charts share the existing weight source. Progress photos are user comparisons, not input to an inferred body-fat score. Every chart needs accessible labels, an equivalent values view, loading/empty/error states, and useful filtering for long histories.

16. **Complete backup, restore, deletion, and recovery as part of the feature.** Add plans, revisions, phases, occurrences, exact completion links, execution snapshots, set/interval data, suggestions/decisions, target periods, daily totals, recovery, waist, and photo metadata/assets to deliberate history backup. Preserve old backup versions and source IDs. A restored plan must use stored dates/status rather than rebuilding from today's date or an AI conversation.

   Keep the portable program export separate from a personal-history backup. Program export contains prescriptions/guidance only; show a review because notes can still contain personal information. Full history backup uses a versioned archive with a manifest, bounded JSON, and separately streamed image assets with digests. Keep legacy JSON import. Do not remove the current size defenses or base64-encode an unlimited photo library into one main-thread JSON string. Initial archive limits: 64 MiB record JSON, 25 MiB per image, 10,000 entries, and 2 GiB total input and expanded bytes, enforced during streaming as well as against declared sizes. Accept only declared record/asset paths; reject absolute paths, traversal, symbolic links, duplicate entries, and corrupted/missing referenced assets before import. Exceeding limits produces an explicit error and offers export without photos where applicable; never omit assets silently. Export communicates whether photos are included. The user chooses an export destination explicitly; do not automatically upload backups.

   Stage restore files, validate the manifest/records/assets, then commit with an interruption-safe journal. After restart, finish or roll back that restore deterministically. Repeated restore is idempotent by stable identity and revision. Save failure must not corrupt unrelated history. Missing photo content never produces a misleading successful full restore; explain the failure or offer an explicitly partial restore with a report.

   Extend all existing Delete All and individual-delete paths, including pending imports, restore staging, timers, notifications, projections, and photo assets. Preserve the existing purge-generation safeguard so an in-flight Health query cannot resurrect deleted local data. Deleting a plan preserves completed activity and personal check-ins unless the user separately chooses their deletion. Deleting an actual workout must update its plan linkage without reviving another occurrence through heuristic matching. Deleting app records does not automatically delete HealthKit samples, original Photos assets, or remote data. Existing source-specific deletion behavior remains explicit.

An interrupted download remains unsaved/retryable, not a broken photo record. On-device AI is optional and independently gated by actual availability; its output goes through the same draft validator.    Inject repositories and value snapshots into Coach view models. Do not keep live SwiftData objects in long-running tasks across contexts. Load the current week/day and chart aggregates rather than observing every set and image in a 26-week plan. Images, JSON parsing, hashing, backup I/O, and interval expansion run off the UI thread.
