# Production storage integration — implementation and acceptance

22 October 2026. Base: PR9 `b1c583027818df7486cc35dbefd890927ee201b7`; the integration below is the current isolated working-source change on top of that commit. The user has now authorized implementing the conservative local-only boundary, explicitly copying retained history, reviewing/pushing the changes, and updating **Pace Full QA** against synthetic data. This supersedes the earlier preparation-only scope.

**Implementation is not acceptance.** This document records source inspection; it does not claim any new test execution, completed independent review, successful build/install, or production migration. No real Health, CloudKit, workout or backup records were accessed for this document. The retained source and remote records must remain unchanged.

The new `CoachPersistenceRegressionChecks+Startup.swift` and additions to `CoachPersistenceRegressionChecks.swift` define actual production startup/migration and backup-restore fixtures. `StorageIntegrationAcceptanceView` provides a Debug-only way to run disposable fixtures and record a result. Their existence is not a passing result. The standalone Python protocol and candidate restore adapter remain supplemental evidence, distinct from executing actual SwiftData paths.

Physical synthetic runs identified SQLite snapshots retaining a WAL header after the backup connection closes, and Core Data changing transaction bookkeeping/entity numbers when the copied schema opens. New snapshots are normalized to rollback-journal mode on their sole writable destination connection. Source access stays read-only. Literal pre/copy/post checks still include every table. Post-schema verification ignores only the enumerated Core Data bookkeeping tables and resolves `Z_ENT` through a validated stable entity-name map; primary keys, revision counters, relationship keys, app fields and external asset bytes remain checked. Unknown new tables or column changes fail closed. The semantic regression fixture explicitly tampers with fields, relationships, entity meaning, tables and columns to require rejection.

Cold WAL files without sidecars have a separate capability result. An exact read-only `SQLITE_CANTOPEN(14)` is reported as unsupported only after the real controller is verified to retain the original file/assets and stay in recovery without selecting a destination. It is not a successful migration. Older schemas with structural column changes, locked-device and power-loss durability, and real integration transitions remain release acceptance gates.

## Remaining integration/acceptance limits

- The actual model graph, all optional fields and relationship/asset variants need complete synthetic coverage. Existing raw-column comparison avoids relying only on the portable backup DTO, but does not by itself certify every supported old schema or OS migration behavior.
- `HealthKitManager` still stores strength/cardio query anchors in app defaults, while `CoachWeightRepository` uses its own protected anchor file. Prove model-commit-before-anchor ordering, idempotent replay and the correct selected-store identity; do not reset real anchors merely because SQLite was copied. No real Health or multi-device CloudKit behavior is established by these fixtures.
- Cover active/paused run recovery and unsaved workout/Coach state through the new startup gate. `RunTracker` resides in `Features/Runs/RunTrackingView.swift`, with auxiliary state in `Services/RunRecoveryStore.swift`. The currently inspected widget renders ActivityKit state; do not add a new shared database merely to create a test seam.
- Missing selected storage fails closed, preserving retained material. A tested forward-recovery journey from the latest local snapshot is still required; automatically reopening a stale legacy source after new local writes remains prohibited. Full device backup/export recovery, lock/reboot, true process termination during commit, physical disk-full and large-history behavior are separate acceptance gates.
- Review failure reports and recovery copy for clear owner actions. Retained cloud copies and older devices are not silently reconciled or deleted. Local copy completeness describes the observed on-device source, not proof that every remote record had downloaded.

PR7's retired-container guard and stale-draft timestamp/revision guard were already fixed before this integration. Retain their regressions; do not list them as newly discovered defects. Preserve the Finish-only control, dismissal autosave, retry queue and banner removal in the separate QA overlay.

## Authorized now; still outside scope

The owner has authorized the source/QA policy: personal fitness history, unknown-provenance records and all restores use the conservative local-only boundary; existing history uses an explicit verified copy and retained originals. These are no longer unanswered design approvals for this integration.

Current authorization does **not** permit applying the migration to the installed production app, inspecting/copying real user records, deleting retained/remote history, changing credentials/entitlements/permissions, live sync experiments, App Store/TestFlight submission, or production release. Before those steps, separately scope the device/account, data categories, operation and recovery destination; approve final release behavior and disclosures. A choice to reconcile or remove old cloud copies requires its own reviewed retention/old-client plan.

The immediate completion sequence is: focused synthetic execution → independent full-integration review and repairs → exact reviewed source push → serial isolated QA build/update → verify launch, existing synthetic QA history and migration/recovery evidence. Record exact results and remaining limits; do not infer them from this checklist. No reset redemption is needed or authorized.
