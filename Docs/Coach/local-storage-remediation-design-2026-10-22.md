# Data-preserving local storage remediation design

22 October 2026. **Proposal only; no production storage changes or real-record inspection.** Source reviewed: PR7 head `0f69a4022f17f54fe54fb5b2d1fc6201a8c75ec2` in `/tmp/pace-coach-release-safety`; comparison main `a3a869f6232bbd970b45951a49f17d7245141120`. Both source snapshots identify version 2.5; the public storefront identifies 2.4. No signed-binary-to-commit mapping was established, so this design describes inspected source, not proven shipping-binary behavior.

The recommended boundary is a protected, explicitly local store for the entire personal record graph, including user-entered fitness history and content of unknown provenance. Retain existing source stores for recovery until a separately approved retention/remediation decision. Do not delete existing cloud records, change entitlements, or disable sync blindly.

## Evidence and scope

The [privacy audit](privacy-growth-audit-2026-10-22.md) distinguishes the code-supported App Review policy risk from proof of actual uploads and from a legal conclusion. A CloudKit-capable configuration does not prove that any particular record was transmitted. A private CloudKit database also does not, by itself, resolve the policy question. Personal-health classification and release approval require owner review against the applicable policy; this document does not decide them.

The [complete field inventory](cloudkit-field-inventory-2026-10-22.json) is the exact schema appendix: **14 legacy model types, 253 stored scalar/blob fields, and 14 relationship declarations**, with source paths, line numbers, and declarations. All 14 model files are identical between the compared main and PR7 snapshots. Computed properties are excluded. The proposed migration preserves every inventoried field and relation, not only those called out below. IDs, timestamps, source labels, status and completion metadata can be personal when joined to their record; none is an automatically safe cloud allowlist.

## Current source behavior to retain and extend

Normal initialization defaults to `.automatic` CloudKit for the 14-type legacy schema (`PersistenceController.swift:119,144–168`). A successful container construction sets `isCloudBacked`; that flag is not proof of network transfer or completed synchronization. The local factory instead creates the 24-type combined schema with `cloudKitDatabase: .none` (`:66–74,105–115`). Coach repository transactions require that local context (`CoachRepository.swift:51–68`).

Current adoption is an explicit user action in the Coach storage review (`CoachHomeView.swift:38–56`). In `PersistenceController.swift:203–244` it:

1. Rejects an already-local/error state or an active recoverable run, then saves the source context.
2. Captures source IDs and a canonical value/relationship digest, allocates a protected unselected destination, and copies the SQLite snapshot plus external blobs.
3. Opens the copied store locally and compares destination IDs/digest and fresh source IDs/digest, also checking unsaved main-context changes.
4. Writes the atomic selection marker last, retires the old container from guarded app imports, swaps the current container, and changes the UI storage generation. There is no suspension between marker commit and in-process swap.

`CoachLocalOwnership.swift:62–87` uses SQLite backup from a read-only source connection, including committed WAL contents. Copying the main SQLite file alone is not equivalent. `CoachLocalOwnership+Assets.swift:8–47` copies the external-storage tree with containment/link checks and before/after SHA-256 validation. `CoachLocalOwnership+Verification.swift:9–38` digests the normalized backup representation, not merely row counts. Coverage must grow when persisted fields or assets are added.

The marker records the selected local directory and retained legacy path (`CoachLocalOwnership.swift:8–13,36–58`). A missing or invalid selected destination produces recovery mode rather than opening a stale legacy store (`PersistenceController.swift:127–142`). Keep this fail-closed behavior. Current adoption is not a general durable resumable migration journal; unselected staging and interrupted selection need an explicit recovery design before broader rollout.

The PR7 generation/retired-container guard cancels guarded app imports and anchor advancement into the old context (`WearableWorkoutInboxService.swift:49–74`). It does not stop another device, prove the old CloudKit coordinator has stopped, or establish remote synchronization completeness. Only the local materialized snapshot is compared. Incoming remote changes or records not yet downloaded need a separate, explicit reconciliation policy; never describe the copy as all cloud history without evidence.

Known ingress to cover beyond Coach includes strength/cardio inbox imports, Health-derived run details/routes, legacy Settings/WeightLog body-mass imports, manual logging, generated plans and backup restoration. The legacy weight paths omit source IDs; preserve `manual_or_legacy` as unknown. The current restore local check is conditional on `file.coach?.hasPersonalRecords`, so legacy-format health/fitness content can otherwise restore into the supplied cloud-capable context (`DataBackupService.swift:635,652–655`). The proposed local boundary must check the destination for **all** personal backup records, across versions 1–5, before database or asset mutation.

## Storage choices

| Choice | Boundary and benefits | Costs and constraints |
| --- | --- | --- |
| **A — All personal records local-only (recommended)** | All existing 14 legacy types plus the ten Coach types live in one explicitly local graph. All personal ingress resolves its destination through one coordinator. This minimizes accidental field leakage, unknown-provenance mistakes and graph splitting. Public bundled catalog data may also remain local. | Legacy automatic cross-device personal sync is not carried forward. Explain local backup/transfer and retained old copies. Existing-user migration and release behavior need approval and validation, not a silent config flip. |
| B — Personal graph local; narrowly defined nonpersonal catalog separate | Create new catalog-only models with an explicit allowlist of curated public exercise/program identifiers, names and published descriptions. Use a separate container and independent model types; no SwiftData relationships across stores. Local records may keep catalog ID/version scalars and their own immutable prescription snapshot. | More schema, versioning and integrity work. Never sync existing `ExerciseDefinition`/template records wholesale: they mix user data and personal links. User-created names, notes, custom loads, selections, usage history, prompts and identifiers tied to a person stay local. A bundled/versioned local catalog may remove the need for CloudKit altogether. |

Do not attempt to make one existing mixed model safe by omitting selected fields from exports while leaving it in a CloudKit-backed schema. Do not split a relationship graph between stores and hope SwiftData resolves it. A separate catalog store does not justify remote cleanup of the retained legacy personal store.

For new installs, an approved release could construct the explicit local container before any personal read/import/write and expose optional Health permission later. For existing installs, detect a known local selection first and preserve it; migrate a legacy selection through the state machine below. Changing defaults, releasing this behavior, and managing old clients remain owner gates.

## Proposed migration state machine

Use a versioned, protected, backup-excluded journal under an app-owned staging root. Proposed stages: `allocated → sourceCheckpointed → copied → verified → selectionCommitted → active`. The journal identifies migration ID, source store ID/schema version, destination ID/schema version, operation generation, checkpoint/digest versions, per-model ID/count digest, asset manifest, import-anchor policy and the last completed stage. Keep raw record values out of logs; journal identifiers/digests are still sensitive metadata and require protection. Atomic writes and tested durability boundaries are required.

1. **Prepare and fence.** Acquire one migration/write coordinator; reject a second migration or concurrent restore. Fence manual writers, app extensions/background writers and async imports through the same storage generation. Resolve or checkpoint a recoverable run using an explicit user decision; do not discard it. Capture active-run state and recheck immediately before selection. A view being disabled is not a complete writer fence. Process-local fencing also does not quiesce remote clients or the framework's cloud activity.
2. **Checkpoint source.** Save all known local contexts or abort, checkpoint the run, capture the source identity, records/relations and required auxiliary state. Define the observed local snapshot boundary and disclose unresolved remote-sync lag. Do not request broader account access merely to make the migration seem complete.
3. **Stage once.** Allocate a unique destination owned by this journal. Use the reviewed consistent SQLite backup and verified external-file copying, or a separately validated versioned record conversion if schemas diverge. Never repurpose the source path. Include every personal type, route/blob, photo reference and required recovery state. Retain original values, IDs, dates and provenance, including nil/unknown values.
4. **Verify before selection.** Open only the staged destination with `.none`. Compare complete schema/version-aware values and relation topology, not counts alone; verify each referenced asset and orphan policy. Recheck the source snapshot and known writers. A mutation, cancellation, low-space error or unsupported schema leaves the old selection intact and the destination unselected. Do not silently omit unknown future fields to obtain a passing digest.
5. **Commit selection last.** Atomically bind destination ID, verified journal/checkpoint, and new generation in the selection record, then swap the in-memory selection and retire old contexts without an intervening suspension. Mark `selectionCommitted`/`active` durably and reconcile this bookkeeping with the selection on launch. A crash after the marker is not permission to repeat the copy or reopen the source. If verification cannot establish an unambiguous selected state, enter recovery without accepting new writes.
6. **Resume safely.** On launch, compare the journal with the actual selection. Resume only an owned, intact, compatible staging operation. If the marker already names this destination, recover/verify it as the selected store; do not insert the same records again. Only an unselected, journal-owned disposable stage may be cleaned after its status is certain. Unknown folders, retained source stores and selected assets are never automatic cleanup targets.

Preserving a local snapshot does not reconcile later changes from older devices. Keep the retained source distinct and read-only to ordinary app writers once selected locally; a future reconciliation feature needs explicit source access, conflict presentation and tested merge rules. No production cloud deletion or entitlement change is part of this state machine.

### Import epochs, anchors and duplicate prevention

Every path must capture the selected store ID plus operation generation, and revalidate after each suspension and at the final mutation/commit/anchor boundary. Retired contexts must remain unwritable even when a caller reads a fresh global generation later. Cover manual/background saves and active-run recovery as well as Health imports. PR7 provides useful guarded imports; extending this invariant across every writer is proposed work, not an asserted completed audit.

Workout/strength query anchors currently live in `UserDefaults` (`HealthKitManager.swift:205–210,255–271`); the modern weight anchor is a protected file under `CoachLocal` (`CoachWeightRepository.swift:14,41–43`). A SQLite snapshot does not by itself snapshot these. Associate new checkpoints with the selected store identity. Preserve copied inbox identities, deletion observations, cutoff dates and query scope; do not reset or advance anchors casually. Commit imported model changes before the corresponding anchor. If an anchor write fails after the model commit, replay must be harmless and the journal must distinguish this state.

Use existing stable record IDs and namespaced Health sample identities for idempotence. For known Health rows, repeated deliveries update the same imported identity; a deletion affects only the explicitly linked imported copy according to the chosen integration semantics. Preserve unknown legacy rows independently: equal date/value is not proof of shared Health identity and must not attach a deletion ID. Do not regenerate IDs on retry, infer provenance, discard one of two conflicting copies, or silently merge matching text. Where an existing ID has different content, retain both evidence sets and surface a deterministic conflict policy instead of claiming a successful identical restore.

An initial or post-marker retry must consult both journal and selected-store state before writing. A committed import batch receives a durable operation identity/checkpoint; a batch whose outcome is uncertain is checked before replay. Enforce one active writer destination. These safeguards prevent migration/restore retries from creating duplicates or applying old callbacks to a new store.

## Backups, recovery and rollback

Local directories and copied assets are explicitly backup-excluded and protected in the inspected implementation (`CoachLocalOwnership.swift:27–34`, `CoachPersistence.swift:21–30`). No equivalent legacy-store exclusion was found; that is a code observation, not a determination about actual device backup contents or policy treatment. Existing protection uses `completeUntilFirstUserAuthentication`; do not describe it as unavailable whenever the device is subsequently locked.

Current history export is an **unencrypted** user-directed file, as Settings explicitly warns (`SettingsView.swift:570`). Version 5 includes bounded record JSON, a manifest and optional photo bytes with integrity digests; `CoachHistoryArchive.swift:44–85` protects the temporary export. SHA-256 detects corruption and does not encrypt or anonymize content. The app must not choose a remote destination or upload the export. A user selecting a Files/share destination is distinct from automatic application CloudKit sync; policy treatment should be reviewed separately.

Before real migration, offer a verified protected recovery snapshot and explain whether it includes photos and all referenced assets. Verify a synthetic round trip first. Retain manifests, schema versions and relevant import checkpoints with recovery material. Keep staged files and temporary exports bounded and protected; cleanup must target only app-owned, unselected/transient files after checking references. If encryption is added, design key recovery and forgotten-key behavior before promising recoverability; encryption is proposed work, not an existing feature.

Current restore already validates bounded archives, stages assets, uses an isolated context, and persists rollback intent before asset cleanup (`DataBackupService.swift:589–648`; `CoachHistoryArchive.swift:87–159`). Retain those safeguards and extend the destination-local requirement to every personal legacy record. Repeated restore, interrupted commit, asset collisions and existing-ID conflicts need explicit tests; a successful format validation alone does not prove lossless reconciliation.

**Rollback depends on whether local writes occurred:**

- Before selection, abort safely with the original selection unchanged; retain recoverable source and journal. A verified unselected stage is disposable, not the source.
- After selection but before any new personal write, rollback still requires checking marker/journal, assets and writer/anchor state. Do not automatically reopen the source merely because launch fails.
- After new local writes, the retained source is stale. Preferred recovery is forward repair or restoration of the latest verified local snapshot into another local store. Reopening the old source loses or hides newer history and can resume undesired cloud writes. Any rollback requiring reconciliation needs a protected copy of both histories, an explicit conflict/delta review, preserved IDs/assets and a newly verified local destination. Never delete the selected local store to make an older source appear current.

## Permission and release gates

| Action | Authorization boundary |
| --- | --- |
| Source review, design documents, isolated code changes, fake Health/CloudKit adapters, synthetic stores/archives, fault-injection tests | Allowed preparation within the current task. Keep test bundles/storage/account dependencies isolated and never open production containers. Test labels must identify synthetic evidence. |
| Read, copy, export, migrate or inspect real Health, workout or CloudKit records | Requires explicit user authorization for the specific device/account, data categories, operation and destination. Current synthetic-only scope does not provide it. Even a read-only record query is outside this scope. |
| Device trust/unlock, Developer Mode, signing/account configuration, or Health/Photos/location/cloud permission prompts | The user/owner must perform or expressly authorize the smallest necessary setup action. Do not assume permission, press through a prompt, create an account or broaden credentials. Report the exact missing step and continue synthetic work. |
| Personal-data migration/default-storage change on existing installations | Requires owner-approved implementation/release plan and informed in-app user choice or an explicitly reviewed migration policy. Preserve recoverable originals. A broad bug-fix authorization does not justify a blind production storage change. |
| Delete remote records, purge a retained source, reset a cloud container or remove backup material | Separate explicit scope and confirmation after presenting affected stores/devices, verified recovery material, retention expectations and old-client recreation risk. Never bundle remote deletion into local adoption or a generic “Delete All” repair. |
| Change CloudKit entitlements, production schema, sync behavior across releases or old-client support | Owner approval plus validated migration/recovery and compatibility plan. No entitlement removal, container replacement, or live sync experiment in this task. |
| Merge, deploy, submit/release App Store builds, edit privacy disclosures or DSA trader/account declarations | Separate owner approval and verified release-to-source mapping. No deployment, submission, account creation or DSA change is authorized here. Prepare reviewable copy/checklists only. |

## Synthetic acceptance before a production proposal

Use the reviewed PR7 tests as a baseline; this design does not claim these additional cases have run. Build each test with explicit `.none` stores, synthetic fixtures, inert service adapters and no production signing/account dependency.

1. Fixture all 14 legacy types, every persisted field/relation, Health-linked and unknown-provenance rows, route/external blobs; separately cover all ten Coach types and photos. Verify byte/value/link fidelity, IDs and ordering-relevant metadata after migration/relaunch.
2. Exercise every personal ingress with a deliberately CloudKit-capable *fake* destination and assert refusal/rerouting before any service/query or mutation: manual writes, imports, plan generation, legacy v1–v4 and v5 backups, run recovery and background callbacks.
3. Inject interruptions before/after each journal and selection durability boundary; low disk, source edits, malformed/missing marker, missing/corrupt assets, unsupported schema and cancellation. Exactly one canonical selection must remain, with recoverable originals and no silent reset.
4. Suspend fake imports at query/metric/asset waits and immediately before commit; migrate, restore, start/checkpoint a run, or retire the old context; resume. Assert no old-store write or stale anchor advance. Test a run starting during the copy and multi-process writer fencing separately.
5. Replay identical import/migration/restore operations, including model commit followed by anchor/journal failure. Assert no duplicate logical records and no inferred deletion identity for unknown-provenance rows. Explicitly test conflicting same-ID content and remote-change simulations.
6. After a selected local write, simulate launch failure and recovery. Assert that the source never becomes canonical automatically, the new record survives a forward recovery, and both histories remain recoverable for a chosen reconciliation.
7. Round-trip backups with/without photos, legacy formats, large bounded fixtures, damaged/truncated input and partial asset installs. Confirm plaintext warnings, optional photo semantics, retained referenced assets and no automatic remote transfer.

Real-device/real-account validation and any production release remain separate gates. No real Health, CloudKit, workout or backup records were accessed for this design; no migration, data deletion, entitlement change, account change or deployment was performed.
